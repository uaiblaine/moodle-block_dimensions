Tokens — Dimensions block

The plugin's whole colour contract is 34 custom properties declared once, on body, with the suffix set byte-identical to local_dimensions' --local-dimensions-* set — only the frankenstyle prefix differs, which is what makes the two plugins one system. Thirty of the 34 are three-rung chains, var(--bs-NEW, var(--BS4-OLD, #literal)): Moodle 4.5 declares zero --bs-* names and Moodle 5.2 declares zero BS4 legacy names, so one chain is correct on every supported branch with no branch test anywhere. Everything below is tokenized as --bk-* for the replica, and the two columns are one contract resolved twice — not two palettes. Measured on the running m502 and m405 stacks on 2026-09-05; the record of both migrations that got here is in token-migration.md.

The plugin authors three colours and no more. shadow, scrim and favourite are the only tokens with a plugin-written dark counterpart, and they are the entire contents of the one activation rule, body[data-bs-theme="dark"], [data-bs-theme="dark"] body: the attribute on body (theme_moove writes it there) or on html (Moodle 5.3 does), never on an element below body. The tokens sit on body rather than :root for the same reason: Bootstrap redefines the --bs-* set on whichever element carries data-bs-theme, and a token declared on html would keep html's light values under a theme that writes the attribute on body. That bound is a guarantee, not a coincidence: the worst a wrongly-firing activation block can do is deepen a shadow, darken a veil and brighten a star — it cannot paint a dark surface on a light page. There is also an @media (prefers-color-scheme: dark) block in the file, and it is deliberately inert: every selector in it is gated on [data-dimensions-media-optin], which nothing in either plugin ever writes, and a test fails the build if it ever becomes reachable. Core treats the OS preference as an input to data-bs-theme, never as an independent trigger, and firing on the media query directly is exactly how a plugin ends up dark inside a light page.

How to read every row below. Three values, in one column: 5.x light, then 5.x dark, then the Moodle 4.5 resolution. They are one declaration seen three ways, not three declarations. On 4.5 a chain lands on its middle rung wherever Boost declares the BS4 legacy name (--white, --light, --gray-dark, --primary) and on the terminal literal otherwise; every literal in the block was chosen to equal the middle rung it stands behind, so the two readings agree today and a test fails the build the day one drifts.

Two names deliberately absent — admin instance data, not tokens

--dimension-custombgcolor --dimension-customtextcolor

These two carry admin-configured colour across the plugin boundary — both card templates write them inline on the article, hex-validated by dataset_provider::sanitize_color(). The mode layer reads them and never declares or overrides them, in either mode, and a test fails the build if any mode block ever assigns one. So a site's chosen brand colour stays its colour when the page goes dark and only the neutrals around it adapt. The same exemption covers the halftone's #00000082 fallback and the print block's literals: dots composite on the admin's own fill or on the decorative gradient, never on the page surface, and paper is white whatever the screen is doing.

Keeping one card warm and the other cool is what distinguishes a competency card from a plan card at a glance, and it survived both migrations. The gradient carries no contrast obligation of its own — the access pill, the favourite disc and the dimension chip all paint their own ground — so the stops are chosen to hold the family in both modes rather than to clear a floor.

The tag chip's default fill is now page furniture, and that closes an open question. It reads var(--dimension-custombgcolor, var(--block-dimensions-surface-inset)) / var(--dimension-customtextcolor, var(--block-dimensions-ink)). The old default was #fd7e14 on the competency card's own #fd7e14 middle stop — 1.00:1, a chip with no edge at all, which token-migration.md logged as open question 2. The section header's second stop is accent rather than brand-fill on purpose: --bs-primary as ink on the dark page is 1.10:1, while --bs-link-color flips to 6.33:1. In dark both stops resolve to the same flipped tint and the fill reads flat, which is legible and deliberate.

The no-JS notice keeps ink rather than warning-ink on its warning ground on purpose: it is the only message a JS-disabled user ever sees, so it holds 14.28:1 light and 11.74:1 dark instead of the 7.82 / 10.32 the tone ink would give.

The eight hand-written dark contrast repairs recorded in token-migration.md are gone, and nothing regressed. Each existed because the light value beside it was a literal: the pending ring, the completed marker and its connectors, the trail-label hover, the select focus ring, the count badge, the mobile filter toggle. All six roles are single declarations now — ink-muted, success-ink, accent, focus-ring, surface — and each resolves correctly in both modes with no second rule to keep in step. The count badge picked up a real improvement on the way: its rest fill was surface-inset, the same value as the platter it sits on, so the chip had no shape at all and only its bold text showed; it is surface now, which gives it a boundary and lifts its ink from 5.99:1 to 7.10:1 in light. That boundary was a faint one, 1.19:1 against the platter in light, and the ink-muted border below is what edges the badge now.

The checked badge draws its outline in brand-ink. Inside a checked status or show-all pill the badge sits on the sliding indicator, which paints surface, and its brand-tint fill stands off that at only 1.33:1 in light and 1.13:1 in dark. So the badge carries a 1px brand-ink border, 14.41:1 and 6.33:1 against the indicator (14.41:1 on 4.5, whose two tokens resolve as in light). brand-edge, core's own border for the pairing, would reach only 1.83:1 and 1.55:1. brand-ink on surface is a row of the contrast pairs at 3:1, and a test ties the badge's border to that row.

The resting badge draws its outline in ink-muted. An unchecked pill paints no fill, so its badge sits on the surface-inset platter, and its surface fill stands off that at only 1.19:1 in light and 1.41:1 in dark. So it carries a 1px ink-muted border too: 5.99:1 in light, 5.38:1 in dark and 6.90:1 on 4.5 against the platter as drawn over the badge's fill — the resting pill and its badge draw at full strength, since an unchecked pill no longer carries an opacity that would fade them. Both badges take padding: 0 5px, the checked one from the resting rule, so the border takes the place of a pixel of padding and neither badge widens its pill. ink-muted on surface-inset is a 4.5:1 row of the contrast pairs, and a test ties this border to it as the other one is tied to brand-ink on surface.
